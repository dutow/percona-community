In my previous blog post about the [PostgreSQL 19 delays](link TODO), I mentioned reverts, or rather, incomplete features, as the main cause behind it.
In this post, I'd like to present a few specific features as a case-study, and show how you could have helped to save the feature, and the release date.

# PostgreSQL Hackers are scary

The PostgreSQL development seems complex, even within software projects:

1. First, you have to go to the mailing list, what is a mailing list even in 2026?
2. Then you have to read through all those scary emails quoting source code fragments
3. Finally, you have to figure out which attachment is the latest patch
4. Download it
5. Apply on top of the postgres sources, which you have to figure out how to get
6. Build everything 
7. And finally start the server up to start testing

And what's even worse, people do throw those source code fragments around in the message, so you assume you also have to.
Even if you find a bug, how can you tell why it is happening?
That question can be hard even for experienced developers joining the project.

Of course, it's 2026, you can ask an AI agent, it will confidently give you an answer you can copy-paste, but let's assume that we are trying to avoid being human carriers posting slop.

# The misconception: a review needs a developer

I'm not saying we don't need all the above, developers discussing code quality and deducing bugs from the source code, because we do.
But, especially with LLMs around, we need something even more important:
people actually trying features out, and saying that it works as they expect it, or the opposite, that it does something confusing.

You don't have to be a developer, anybody familiar with databases and PostgreSQL can help the project:
read the feature description, start up the server, try it out!
And maybe it's easier, because if you just started to read the documentation, and start scratching your head, thinking that something doesn't amke sense there, then you found an issue without even sending a single SQL command to psql.

And before you can complain about the difficult steps above, I want to iterate back to the mentioned reverts:
because some of the reverted features should have been raised many eyebrows at that step, simply when people read the documentation of the feature.
Other features should have raised questions when people tried to execute simpler or more trickier scenarios with them, and then sending confused "Why is this happening?" questions to [bugs](https://www.postgresql.org/list/pgsql-bugs/) or [hackers](https://www.postgresql.org/list/pgsql-hackers/).

Those feature were committed and were easily available for anybody using the [development snapshots](https://www.postgresql.org/download/snapshots/) after that.
Despite the scary name, those are essentially what most projects call "nightly builds", a release built from the master branch periodically.
These make it easy for anybody to try out already committed features.

# Try out in progress patches with Hackorum

And I also want to reiterate my point from the previous blog post:
Now the CI on [hackorum.dev](https://hackorum.dev) automatically publishes a docker image for every patch submission.

If you find a thread with an interesting patch, all you have to do is execute:

```
docker run --rm -p 5432:5432 ghcr.io/hackorum-dev/postgres-patch:t<THREAD-ID>
```

Where `<THREAD-ID>` is the numeric identifier you can also see in the navbar, and every thread shows the exact, specific command.

This allows you to test features, or bugfixes to features even before they become part of the main postgresql development branch.
